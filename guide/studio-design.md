# The listener’s studio

Djound starts with a recording the listener knows. Success is hearing a new instrumental they would keep, asking for one more change in their own words, and coming back to the version they loved. The Final Fantasy listening sessions give this design a concrete test. After changing the band, could someone say “I like those piano replies. Let the accordion sing a little more,” hear the difference in the same phrase, and keep the result? [Product direction and listening sessions](product.md)

## Selected design

The selected studio puts take history on the left. The song, its current take and the export action share the top of the listening area. The waveform, comparison buttons and edit field follow in that order. Each request names the take it will change. On a phone the same controls stay in reading order, with history available in a disclosure. The library uses the same wordmark, graphite surfaces, lime accent and recording covers. ## From the first listen to a favorite

| Step | Interaction | What the listener can count on |
| --- | --- | --- |
| Bring a recording | Import from the library using a file picker or drop. A new library gives the import action priority. A returning library gives the recordings priority. | Show the actual input rules at the picker. The current backend accepts one MP3, WAV or M4A, 1 second to 5 minutes, up to 64 MiB. A successful import opens its Original. A validation error leaves the picker usable. |
| Choose a sound | Play Original, then choose a suggested sound or type a direction. A suggestion can fill the composer so the listener can add “with a cello” before making the take. | The chosen direction and the take it will change are visible together. Suggestions are starting points. A listener can type tango, reggae, a mood, or an individual change without finding a matching genre button. |
| Wait and listen | Submit once. Display the request against its parent and report the worker’s actual stage. A ready result offers playback. | The original or a prior take stays playable. A job finishing while the listener is playing another version leaves that audio alone. A restored session distinguishes a queued job, a running job, and a finished take. |
| Make one more edit | Choose a working take. In the same composer, describe what to keep and what to change. For a passage, expose start/end controls and a short preview on that take’s timeline. | The new take branches from the visibly selected version. The old one remains available. Recorded parent, submitted words, and actual changed range travel with the child. Range controls also work with a keyboard. |
| Compare one phrase | Toggle playback between the working take and its parent or Original. Preserve play/pause and use the stored song-time mappings to carry the listener to the corresponding phrase. | Auditioning a reference leaves the working take, composer draft and selection alone. Label what is playing and what the next request will edit. Selecting a history row explicitly changes the working take; a comparison button only changes the audio being heard. |
| Keep and return | Keep one completed take as the recording’s favorite. Open another take, try another branch, or export a WAV. | A new favorite replaces the prior favorite. Keep and Export name the working take and continue to act on that exact ID while a comparison source is playing. Its earlier takes stay in history. Export downloads the same stored audio. Reopening from the library returns to the favorite. |

## When the happy path breaks

* **A connection drops during import or submission.** Show the pending filename or prompt and an explicit Resume action. Reuse the saved file, parent, bounds and idempotency key. A refresh or double click must never create a second take for one request. [Recoverable requests](../web/src/renditions/useRecoverableRequest.ts)
* **A take needs clarification.** Show the original request in its history position. For a retained passage, offer the server’s two choices about keeping its exact sound or applying the new change there. For a general clarification, restore the request, its parent and any passage bounds for editing. A new audition cannot change which question a reply answers.
* **Generation or playback fails.** Keep completed audio playable, show the specific failure beside the affected take, and offer a usable retry or revised prompt. Give a failed library load its own retry state. Distinguish no recordings from no search results and from an unavailable server.
* **The tune sounds wrong.** Make Original one comparison away. Let the listener return to the previous take or give a new direction. Djound can miss quiet notes and pick up nearby instruments, so a completion indicator means the take is ready to hear.
* **A project link is stale.** Show the missing-recording state with a way back to the library. When only the requested take is unavailable, identify the fallback take so the next edit has an unambiguous parent.

## Components and responsive behavior

The library needs a workspace navigation, import control, search and favorite filter, and recording rows with a clear open action and an overflow menu. Show information the server can verify, including duration and ready take count. Display the imported name without its audio extension when there is a readable stem; preserve the original filename for source details.

The studio needs a take player, a comparison control, a direction composer, a passage selector, take history, and actions for keeping and exporting. The player owns one audio element and the actual media clock. If the visual direction uses a waveform, derive its peaks from the heard recording, provide a normal seek control while peaks load or on failure, and expose an accessible time slider. History identifies parentage and the favorite. A status announcement should announce meaningful transitions once, without reading the entire history on each poll.

At wide widths keep playback, the edit target and the composer visible together. Let history occupy a secondary column. On a narrow screen keep the title, active take, play/seek, and composer in reading order. Move take history into an accessible sheet or disclosure, with the current take indicated in its trigger. Keep passage controls, clarification choices and export reachable without hover. Restore focus after dialogs and keep the composer usable with the mobile keyboard open.

## Backend decisions

The project detail already supplies original and take audio URLs, durations, request IDs, parent IDs, favorite ID, applied ranges, status, and the piecewise-linear time map used for comparisons. Each ready take already has a WAV export. These flows need a reorganized client and durable selection rules. An external share link, collaborative account system, and new inference model are outside this design. [API contract](../contracts/openapi.yaml) · [Playback position mapping](../web/src/renditions/songTime.ts)

The existing recording index returns only ID and title. Extend the list response in one query with original duration, number of ready takes, and favorite identity and label. If the interface offers recent sorting, return a real timestamp with a defined meaning. Invalidate the list after import, a newly ready take, favorite changes, moving to Trash and restoring. Old and empty projects must appear without fetching each project’s full history. [Current index and project detail](../server/src/main/java/com/djound/rendition/RenditionProjects.java)

Put **Move to Trash** in a recording’s overflow menu. Confirm the recording name and explain that its original, takes and favorite will move together. Offer Undo after the move and Restore in Trash after a reload. Opening an old link to a trashed recording should offer to restore it. Moving a project to Trash keeps its audio on disk. Existing WAV exports remain available to their owners. Permanent purging and removal of individual takes are separate storage features.

Store a nullable trash timestamp on the recording. The normal library excludes those rows; the Trash collection returns them. Use an idempotent state change for move and restore, backed by a transaction that locks the same project row as a new request. Moving a recording with a queued or running take returns 409 with an actionable message. Recording submission, favorite changes and audio access must respect the trash state even from a stale open tab. Keep every take, favorite, clarification and audio file attached to the same recording ID so a restore reopens the intact project. Check the operation using disposable data with multiple takes, a favorite, an active job, a repeated request, a stale tab and a restart. [Project and take relationships](../server/src/main/resources/db/migration/V13__recording_renditions.sql) · [Stored clarification relationships](../server/src/main/resources/db/migration/V15__rendition_passage_answers.sql)
